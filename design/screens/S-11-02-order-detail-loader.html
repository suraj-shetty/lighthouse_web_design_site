Layout

  • This screen has no content of its own. It shows the detail skeleton while GET /v1/rfqs/{id} runs, then is replaced by the screen for the order status.
  • Routing: requested / quoted / unknown → S-11-03 · quote_accepted / delivery_rejected → S-11-07 · delivery_submitted → S-11-08 · completed / cancelled / declined → S-11-11.
  • 375 — full-screen skeleton, or a centred error block. 768 — same, centred. 1440 — skeleton in the two-column detail layout.
  • States: default and loading are the same skeleton · error "Could not load order details" + toast · missing-id "Order id is missing" · unknown-error "Something went wrong" + toast.

Components used

  • Navigation shell (shared) · Top header (back only)
  • Skeleton (detail)
  • Empty state, error variant · Button filled S (RETRY) · Button text (View My Orders)
  • Toast danger ("Load failed")

Motion

  • Skeleton to the status screen — --skel-*, --shimmer-*, --reveal-*
  • RETRY press — --press-*; "View My Orders" — --page-slide-*; toast — --toast-*

Accessibility

  • A polite status says "Loading order" while the skeleton shows.
  • The error block is an alert; RETRY is the first focus target, then "View My Orders".
  • The page keeps a visually hidden h1 "Order details" until the status screen supplies its own.

Decisions to confirm

  • The app shows no header or back control in the error state; web keeps a Back button in the bar (web addition).
  • In the mockups, list rows link straight to the status screen (S-11-03 / 07 / 08 / 11) so the flow can be clicked through; in the product they pass through this loader.
  • Offline is not handled in the app; it surfaces as "Load failed / Network error occurred".
